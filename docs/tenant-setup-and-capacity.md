# Geographic choices, primary contact role and tenant capacity

## Existing behavior retained

Angular tenant forms, Rails persistence, shared platform reference options, assigned-administrator authorization, explicit one-time invitations, Tenant Admin memberships and Apartment schema isolation are reused. Country and time zone were optional free-text metadata. Tenant creation previously opened its edit screen. Seat/module rules were previously undecided; this update approves user limits only, not CPQ modules or subscription plans.

## Current contract

- `country`: optional ISO country code from the server's TZInfo country data. Legacy saved country strings remain readable/editable and display as a fallback until a catalog choice replaces them.
- `time_zone`: optional standard IANA identifier. Searchable labels include the current UTC offset; offsets are display-only and may change seasonally. The identifier is persisted, never the label or a fixed offset.
- `user_limit`: required positive JSON integer, maximum PostgreSQL integer `2147483647`. The same server rule applies to creation and updates. The UI accepts decimal whole-number input, not fractions, negatives or scientific notation.
- `primary_contact_role`: `tenant_admin`, currently the only valid tenant role. Defaults to Tenant Admin in setup and is stored on the tenant alongside its primary contact. Platform roles are never accepted. Because no lower tenant role exists, this selection cannot remove the tenant's administrative invitation path.
- `occupied_seats`: server-derived distinct normalized email count across enabled users with enabled tenant memberships, usable unaccepted invitations, and the tenant's primary contact reservation. Multiple contacts alone do not occupy seats; the primary contact always reserves one. Expired/revoked invitations and disabled memberships/users do not count, except when that email is independently reserved by the primary contact or another usable invitation. Resending and accepting invitations never double-count the same email.

Primary-contact role selection is an **access intent/reservation**, not automatic account activation. Use the existing Tenant access page's explicit primary-contact action to populate the invite form, then generate and share a single-use invitation link. Acceptance creates/enables only that tenant's Tenant Admin membership. Existing users authenticate using their existing password; memberships in other tenants are unchanged. MFA and Active-tenant checks remain enforced. Manual sharing remains the approved delivery mechanism; SMTP is not introduced.

## Reference data and industries

`GET /api/v1/reference_options` additionally returns `countries`, `time_zones`, and `can_manage_industries`. Country and time-zone choices are loaded through the existing route resolver. Raw Materials, Services and Manufacturing are additive shared industry defaults; existing industries are preserved.

Custom industries use existing `POST /api/v1/reference_options` permissions: **Super Admin only**, shared platform catalog. The create/edit form exposes “Create your own industry” only when the API grants catalog-management permission. The UI explains that names become shared catalog entries; private tenant data is not collected here. Assigned CPQ Admins can select existing options and edit their assigned tenants but cannot create catalog entries. A tenant-private industry catalog is not introduced without a separate data-scope policy.

Names are trimmed, nonblank, limited to 120 characters, and unique ignoring case/outer whitespace. Model validation and a partial unique database expression index cover ordinary submissions and races. The generated custom code is selected automatically and sent in the tenant payload. The catalog request completes before the tenant save; if the tenant request fails, the valid catalog entry remains, is already selected in the retained form, and is reused on retry. No duplicate entry is generated by that retry.

## Capacity consistency and migrations

Invitation issue/resend and acceptance, membership enable/create, user activation, and tenant updates serialize capacity checks under the same tenant row lock. Acceptance locks tenant before invitation to match issuance order. A full tenant returns `seat_limit_exceeded` (409). A limit reduction or contact change that would exceed occupancy returns the established field-error shape (422). Errors leave the form's values intact. Lifecycle status does not release seats; disabled access does not silently change the commercial capacity.

Forward migration `20261026000300` adds capacity and primary-contact role with database checks. Existing tenants are backfilled to `max(1, occupied seats)` rather than inventing purchased capacity. Review and increase these limits before inviting additional users. Existing accounts, passwords, tenant schemas and contacts are retained. A local pre-migration database backup is ignored under `backend/tmp` and must never be committed.

Apartment's task flag is now set before rake tasks load: `db:migrate` handles shared/public migrations, while `platform:migrate_tenants` uses the existing tenant-only migration directory. This avoids replaying shared-table migrations inside tenant schemas.

```powershell
docker compose -p cpq-integration exec backend bin/rails db:migrate
docker compose -p cpq-integration exec backend bin/rails platform:migrate_tenants
```

Use the existing isolated local project and database; do not reset or remove database volumes.

## Completion behavior and evidence

Successful creation navigates to the existing `/tenants` home page, clears prior directory filters, requests current API data, and displays **Tenant created successfully.** A one-time session-storage notice survives navigation; it is not inferred from an arbitrary URL parameter. Failed saves keep the user on the form with entered details and useful errors. Editing keeps its existing saved confirmation.

Tests cover keyboard selection, stable geographic identifiers, custom-name normalization/duplicates/permissions, valid and invalid capacity, failure preservation and redirect notice, pending/primary/active deduplication, invitation acceptance, limit reduction, activation enforcement and concurrent last-seat invitations. Full test/build results and live verification are recorded in the implementation handover; no production or four-laptop acceptance is implied.

Local evidence: 82 frontend tests passed; 94 Rails tests / 823 assertions passed, followed by 21 focused Rails tests / 163 assertions including the additional cross-tenant acceptance scenario. Production build passed with advisory size warnings (initial bundle approximately 501 kB; existing component styles remain below error thresholds). No size budgets were relaxed. Live browser checks created the clearly named synthetic verification tenant, checked the success redirect/current directory, saved an edit and confirmed geographic identifiers/custom industry/capacity survived a full reload. Invitation acceptance, over-capacity activation and concurrent last-seat attempts were verified in the isolated PostgreSQL test environment; no real recipients were invited for QA.
